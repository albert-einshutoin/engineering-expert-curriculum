1. なぜ重要か

Kernel Optimizationは、GPU・HPC・Acceleratorにおいて「高性能カーネルを測定し最適化できる」ための中核テーマです。実務では単独で現れるより、周辺の概念や制約と組み合わさって現れます。そのため、用語の定義だけでなく、どの条件で使い、何を保証し、どこで破綻するかを一つのモデルとして理解します。

このLessonでは、tiling、fusion、vectorization、autotuningを同じ地図上に配置します。専門家は「知っている技術の数」ではなく、問題を正しい抽象度へ置き、必要な証拠を集め、複数案から条件付きで判断できる人です。

講義本文: tilingはdataをfast memoryへ分割reuseし、fusionはintermediate write/readとlaunchを減らします。vectorized load、unroll、occupancy、instruction mixをprofileします。単一kernel最速ではなく、end-to-end graphのtransfer、synchronization、batch、tailを含めて最適化します。

3. メンタルモデル

  1. Kernel Optimizationを「入力 → 状態 → 規則 → 出力」の流れで整理する。
  2. 各概念（tiling、fusion、vectorization、autotuning）の違いを一文で説明する。
  3. 小さな具体例を手作業で追跡し、用語と挙動を結びつける。
  4. 成立条件と、成立しない反例を一つずつ用意する。
注意: 図や比喩は理解を助けますが、保証ではありません。境界条件と反例を一緒に持つことで、比喩の誤用を防げます。

4. 学習・実装手順

  1. 用語を自分の言葉で定義し、似た用語との差分を書く。
  2. 最小の入力例を作り、状態がどう変化するかを追う。
  3. 結果を予測してからコード・計算・観測で確かめる。
  4. 予測との差分を「前提の不足」「観測の不足」「理解の誤り」に分類する。

最小実験

// CUDA-style pseudocode
__global__ void transform(const float* input, float* output, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        output[i] = input[i] * 2.0f; // tiling
    }
}
// Check memory access, occupancy, and fusion.

コードは完成品ではなく、観測可能な最小実験の出発点です。自分の環境で動かし、前提と結果を記録してください。

5. 設計判断とトレードオフ

基礎段階では網羅性より、概念間の境界を正確にすることを優先します。便利な比喩は入口として使えますが、比喩が成立しない条件も必ず確認してください。

観点確認する問い
正しさどの不変条件を守り、どの入力・並行性・障害まで保証するか。
性能時間、空間、I/O、ネットワーク、待ち行列のどこが上限になるか。
安全性悪意ある入力、権限境界、情報漏えい、誤操作にどう耐えるか。
変更容易性要件変更時にどの境界まで影響し、互換性をどう維持するか。
運用性失敗をどう検知し、誰が何を見て、どの手順で復旧するか。

6. 典型的な失敗

  • tilingとfusionを同じものとして扱い、境界条件を失う。
  • 小さな成功例だけで一般化し、入力規模・並行性・障害時に破綻する。
  • 結果だけを確認し、途中状態や観測証拠を残さない。
  • 採用した方式の前提条件と、撤退条件を記録しない。
