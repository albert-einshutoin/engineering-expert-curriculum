Indexと実行計画
応用Lesson

RDB、NoSQL、ストレージエンジン、トランザクション、索引、検索を内部構造から理解し、要件に合う永続化を選ぶ。 このLessonでは「内部機構、設計判断、実装方法を具体化する」ことに集中します。

1. なぜ重要か

Indexと実行計画は、データベース・ストレージ・検索において「遅いクエリを計画と統計から改善できる」ための中核テーマです。実務では単独で現れるより、周辺の概念や制約と組み合わさって現れます。そのため、用語の定義だけでなく、どの条件で使い、何を保証し、どこで破綻するかを一つのモデルとして理解します。

このLessonでは、B+tree、hash index、selectivity、cost-based optimizerを同じ地図上に配置します。専門家は「知っている技術の数」ではなく、問題を正しい抽象度へ置き、必要な証拠を集め、複数案から条件付きで判断できる人です。

講義本文: B+tree indexはsorted keyでpoint/range検索、hash indexはequalityへ適します。optimizerは統計からcardinalityとcostを推定し、scan、join order、join algorithmを選びます。selectivity、composite key順、covering、partial/function index、stale statistics、parameter sensitivityをplanと実測で確認します。

2. 中核概念

B+tree

内部nodeにseparator key、leafにsorted entryを持つ平衡多分木で、range scanとdisk page単位のindexに適します。 実装では境界値、資源使用量、失敗時の挙動、代替方式との比較まで確認します。

hash index

「hash index」を実装や設計へ落とす際は、正常系だけでなく境界値、競合、失敗、観測方法を同時に扱います。別の選択肢と比較し、性能・安全性・変更容易性・運用コストのどれを優先したかを記録してください。

3. メンタルモデル

  1. Indexと実行計画を構成する責務を分け、境界ごとの契約を定義する。
  2. 代表的な実装を一つ作り、計算量・資源・失敗経路を測る。
  3. 代替方式を最低二つ比較し、採用条件と不採用条件を明示する。
  4. ログ、メトリクス、テストなど、正しく動いた証拠を実装に含める。
注意: 図や比喩は理解を助けますが、保証ではありません。境界条件と反例を一緒に持つことで、比喩の誤用を防げます。

4. 学習・実装手順

  1. 要件を機能要件・非機能要件・制約へ分解する。
  2. 最小実装を作り、正常系と境界値を自動検証する。
  3. 一つの障害を注入し、期待する失敗モードと復旧を確認する。
  4. 計測結果を基に設計を一度変更し、差分を記録する。

最小実験

BEGIN;

SELECT id, version
FROM learning_state
WHERE topic = 'B+tree'
FOR UPDATE;

UPDATE learning_state
SET version = version + 1, updated_at = CURRENT_TIMESTAMP
WHERE topic = 'B+tree';

COMMIT;
-- hash index: 実行計画と競合も必ず確認する

コードは完成品ではなく、観測可能な最小実験の出発点です。自分の環境で動かし、前提と結果を記録してください。

5. 設計判断とトレードオフ

応用段階では、正解を一つに固定せず、どの条件でどの方式が有利かを判断します。性能・整合性・安全性・開発速度・運用負荷は同時に最大化できないため、優先順位を明示します。

観点確認する問い
正しさどの不変条件を守り、どの入力・並行性・障害まで保証するか。
性能時間、空間、I/O、ネットワーク、待ち行列のどこが上限になるか。
安全性悪意ある入力、権限境界、情報漏えい、誤操作にどう耐えるか。
変更容易性要件変更時にどの境界まで影響し、互換性をどう維持するか。
運用性失敗をどう検知し、誰が何を見て、どの手順で復旧するか。

6. 典型的な失敗

  • B+treeとhash indexを同じものとして扱い、境界条件を失う。
  • 小さな成功例だけで一般化し、入力規模・並行性・障害時に破綻する。
  • 結果だけを確認し、途中状態や観測証拠を残さない。
  • 採用した方式の前提条件と、撤退条件を記録しない。
  • テスト環境と本番環境の差を無視し、性能・権限・時刻・ネットワーク条件が再現されない。

7. 演習

  1. Indexと実行計画を扱う小さな実装を作り、正常系・境界値・失敗系のテストを追加する。
  2. B+treeを採用する案とhash indexを採用する案を、性能・安全性・変更容易性・運用負荷で比較する。
  3. 実装へ計測点を追加し、少なくとも3回測定して結果とばらつきを記録する。

8. 理解度チェック

Indexと実行計画の実装を選ぶ際の主要なトレードオフは何ですか？

性能、整合性、安全性、開発速度、運用負荷、変更容易性から、今回重要な軸を選び、条件付きで比較します。

正常に動くことと、正しく設計されていることの違いは何ですか？

正常例の成功は一つの観測にすぎません。境界、失敗、競合、資源制約、将来変更でも不変条件が保たれる必要があります。

実装を本番へ出す前に何を観測可能にしますか？

入力規模、処理時間、失敗種別、資源使用量、重要な状態遷移、相関IDを候補にします。
