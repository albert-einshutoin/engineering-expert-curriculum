なぜ重要か

並行処理では、同じコードが正しい順序で動くという暗黙の期待が壊れる。二つのworkerが在庫を一つずつ減らすだけでも、読取りと書込みが分離していれば更新を失う。低頻度の競合を「再現しないから直った」と扱うと、負荷が高い本番で不変条件を破る。

プロセスは独立したアドレス空間を持つ実行環境、スレッドはプロセス内の資源を共有する実行単位である。ただし、常にプロセスが重くスレッドが軽いという一軸では選べない。生成方式、OS、通信量、権限境界、クラッシュ時の巻込みが判断を変える。

断定への注意: このラボの基準はJava SE 21である。Javaのvolatileはvisibilityとorderingに関する同期関係を作るが、複合incrementのatomicityは保証しない。C/C++のvolatileは別の言語契約であり、Javaの説明を移植しない。lockを置くだけでdeadlockが消えるわけでもない。

メンタルモデル

並行性の正しさを四つに分ける。atomicityは操作が途中状態を見せないこと、可視性は一方の書込みを他方が観測できること、順序性は必要な前後関係が成立すること、停止性は処理がいつか進むことである。一つを満たしても他を自動では満たさない。Java SE 21では、あるvolatile書込みは同じfieldへの後続volatile読取りにhappens-beforeするが、stock--全体はread、compute、writeの複合操作である。

「data raceがない」と「業務上のrace conditionがない」も別である。個々のアクセスがatomicでも、在庫確認と確定の間に別操作が入れば業務不変条件を破り得る。守る範囲はコード行ではなく状態遷移で決める。

動く例で考える

lost updateをイベント列で再現する

次をRaceLab.javaとして保存する。racyとsynchronizedは同じJava 21、初期値、worker数、反復数、出力契約を使う。

public final class RaceLab {
    private static final int INITIAL = 1000;
    private static final int PER_WORKER = 500;
    private static final int TRIALS = 200;
    private static final Object LOCK = new Object();
    private static volatile int stock;
    private static boolean synchronizedMode;

    private static void decrementMany() {
        for (int index = 0; index < PER_WORKER; index++) {
            if (synchronizedMode) {
                synchronized (LOCK) {
                    stock--;
                }
            } else {
                int observed = stock;
                Thread.yield();
                stock = observed - 1;
            }
        }
    }

    public static void main(String[] args) throws InterruptedException {
        if (args.length != 1
                || (!args[0].equals("racy")
                && !args[0].equals("synchronized"))) {
            throw new IllegalArgumentException(
                    "usage: java RaceLab racy|synchronized");
        }
        synchronizedMode = args[0].equals("synchronized");
        int violations = 0;
        int minimum = Integer.MAX_VALUE;
        int maximum = Integer.MIN_VALUE;
        for (int trial = 0; trial < TRIALS; trial++) {
            stock = INITIAL;
            Thread first = new Thread(RaceLab::decrementMany);
            Thread second = new Thread(RaceLab::decrementMany);
            first.start();
            second.start();
            first.join();
            second.join();
            int observed = stock;
            if (observed != 0) {
                violations++;
            }
            minimum = Math.min(minimum, observed);
            maximum = Math.max(maximum, observed);
        }
        System.out.printf(
                "mode=%s trials=%d violations=%d min=%d max=%d%n",
                args[0], TRIALS, violations, minimum, maximum);
        if (synchronizedMode && violations != 0) {
            throw new AssertionError("synchronized invariant failed");
        }
    }
}
java --version
javac RaceLab.java
java RaceLab racy | tee race-before.txt
java RaceLab synchronized | tee race-after.txt

出力契約はmode=... trials=200 violations=... min=... max=...の一行である。racyで違反が一度も観測されない実行も仕様上あり得るため、一回の非再現を修正証拠にしない。synchronized側はコード上のmonitor関係と200試行の違反0を組にし、どちらか片方だけを証拠にしない。

前提
Java 21、在庫1000、platform thread AとBが各500回、一件ずつ在庫を減らす。不変条件は最終値0かつ途中で負数なし。
入力
同じ1000件の減算命令を二workerへ均等配分し、racyとsynchronizedを各200試行する。
操作
volatile int stockのread、subtract、write間へyieldを挿入したracy版と、三操作全体を同じmonitorで囲む版を実行する。
観測
Aが値10を読み、Bも10を読み、Aが9を書き、Bも9を書くと二件処理して一件しか減らない。100試行中37試行で最終値が1以上なら不変条件違反である。
結論
synchronizedでread-modify-write全体を囲む。修正後200試行で違反0でも確率だけの証明にはせず、monitor unlockから後続lockへのhappens-beforeと試験結果の両方を証拠にする。

性能も同条件で測る。仮に同期なし中央値18ms、mutex 31ms、message passing 44msなら、mutexの13ms増は正しさの費用である。process案は障害隔離を得るが、serializationとcopy、監視、再起動契約を追加する。

ラボ成果物: 「競合を再現し不変条件で修正した実験記録」には、失敗頻度、最小interleaving、同期前後のコード差、停止性、性能分布を含める。

もっともらしい誤診と反証

  1. 誤診: 「二workerが止まったのでdeadlock」。反証: lock取得と待機の循環を記録する。I/O待ちなら外部完了で進み、starvationなら他workerだけ進捗する。停止だけでは循環待ちを証明しない。
  2. 誤診: 「Java volatileを付けて100回通ったのでrace修正済み」。反証: read-modify-writeをeventへ分解し、同じinterleavingがJava Language Specification上可能か確認する。volatileがvisibilityとorderingのhappens-beforeを作っても複合incrementのatomicityを保証しない。

lock範囲を広げると不変条件は守りやすいが並列性が下がり、複数lockは並列性を上げる一方で順序規約が必要になる。timeoutでlockを諦める場合も、途中状態のrollbackまたは再試行契約が要る。

知識チェック

  1. 整数代入がatomicならcounter増加もatomicか。通常は同じではない。増加はread、compute、writeの複合操作になり得る。
  2. process間ならraceは起きないか。共有memory、file、databaseを介せば起きる。address space隔離は全資源の隔離ではない。
  3. lockを一つにすればdeadlockは消えるか。そのlock同士の循環は避けやすいが、callback、I/O、再入、別資源待ちを含む停止性は別に確認する。

5分teach-back

lost updateの四イベントを描き、不変条件、atomicity、可視性、停止性を区別する。mutex案とmessage passing案の障害半径を一つずつ述べる。

未知へのtransfer

プロセス分離とスレッド共有の再比較を、画像変換pluginまたは機密データ集計へ適用する。CPU時間だけでなく、権限、入力の信頼度、IPC量、worker crash後の再実行を評価し直す。
